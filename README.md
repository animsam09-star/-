# 상승 종목 원인·파급 분석 파이프라인

최근 주가가 강하거나 상승 전환한 KRX 종목을 스크리닝하고, 상승 **원인**을 뉴스·공시로 분류한 뒤,
원인이 **산업 공통 요인**일 때 동종업계·전방·후방 산업의 수혜 후보를 예측하는 자동화 파이프라인.

## 파급에는 두 개의 축이 있다

이 파이프라인의 핵심 설계입니다.

**수직축 (밸류체인)** — 제품·물량이 흐르는 경로(후방 소재·부품 ↔ 기업 ↔ 전방 수요처).
수주·공급계약처럼 물량이 전이되는 원인에서 작동하며 **시차가 있습니다**(조선 수주 →
기자재 발주까지 6~12개월). 시차 덕분에 선점 기회가 큽니다. `valuechain/*.yaml`이 근거입니다.

**수평축 (공통 동인)** — 같은 매크로·정책·원자재 동인에 노출된 기업 집합으로,
**섹터를 관통합니다.** AI 데이터센터 동인 하나가 반도체·전력기기·건설·공조·전선·원전을
동시에 건드리는데, KRX 업종 분류로는 이게 전부 흩어져서 잡히지 않습니다. 업황·정책·원자재
원인에서 작동하고 **동시에 반응**합니다. 테마지수·ETF 구성종목과 팩터 베타가 근거입니다.

원인 유형이 어느 축을 탈지 결정합니다. 수주·공급계약이면 수직, 업황·정책·원자재면 수평입니다.

수평축에서는 두 가지가 결정적입니다. **첫째, 부호**입니다. 구리 상승은 비철 제련에 수혜지만
전선에는 원가 부담이므로 무조건 수혜로 몰면 반대 방향으로 갑니다. **둘째, 동시성** 때문에
목록만으로는 알파가 없습니다. 실제 기회는 "노출도는 높은데 아직 반응하지 않은 종목"이고,
이걸 **갭**으로 정량화합니다.

```
갭 = 기대수익률 − 실제수익률
기대수익률 = β_시장 × 시장 최근수익률 + β_그룹 × 그룹고유 최근수익률
```

시장 요인을 분리하지 않으면 모든 종목이 시장을 통해 서로 상관되어 그룹과 무관한 종목까지
'미반영'으로 잡히므로, 그룹 수익률에서 시장 성분을 제거한 잔차를 그룹 고유 요인으로 씁니다.

## 계층 구조

두 축이 **하나의 관계 그래프**에서 만납니다. 이게 시스템의 뼈대입니다.

```
Layer 0  종목 마스터    src/universe.py    티커·정식명·시총 — 이름→티커 해석의 단일 출처
Layer 1  관계 그래프    src/graph.py       모든 관계를 하나의 엣지 테이블로
                      src/graph_build.py   밸류체인 YAML·테마·ETF·팩터 → 엣지
                      src/dart.py          DART 사업보고서 원문 수집
                      src/dart_extract.py  공시 → 수직축 엣지 (인용 검증)
Layer 2  추론          src/analyze.py     원인 판정 → 그래프에서 후보 조회 → LLM이 선별·부호판정
Layer 3  채점          src/score.py       엣지 단위로 성과 누적
```

**Layer 0이 스크리닝과 독립적인 것이 중요합니다.** 예전에는 종목명 인덱스를 스크리닝
결과에서 만들어서, 시총·거래대금 필터에 걸리는 소형 후방 소재주 — 수직축이 잡아내야 할
바로 그 대상 — 는 티커 해석 자체가 불가능했습니다.

### 관계 그래프

노드가 세 종류, 엣지가 네 종류입니다.

```
T:005490  종목        (T → I, 소속)   이 종목은 이 산업에 속한다
I:시멘트   산업        (I → I, 후방)   dst는 src의 후방(소재·부품·장비)
D:구리    동인        (I → I, 전방)   dst는 src의 수요처
                     (T → D, 노출)   sign이 부호, weight가 강도(β)
```

**회사↔회사가 아니라 이분 그래프인 이유**는 조합 폭발 때문입니다. 구성종목 80개 ETF를
회사 쌍으로 저장하면 3,160개 엣지지만, 동인 노드를 경유하면 80개입니다. 부수 효과가 더
중요한데, **채점 단위가 엣지가 됩니다.** "건설·EPC→후방→시멘트" 경로가 지금까지 몇 번
맞았는지 누적되면, 밸류체인이 고정 지식이 아니라 성과로 갱신되는 자산이 됩니다.

엣지에는 수명이 두 종류입니다. **`graph/edges.jsonl`**(커밋)은 밸류체인·DART에서 나온
수직축 관계로 느리게 변하고, **`data/edges_{date}.jsonl`**(비커밋)은 테마·ETF·팩터 베타에서
나온 수평축 노출로 매일 재계산됩니다. 추론 시점에 둘을 합쳐 하나로 봅니다.

## 동작 흐름

```
1. 스크리닝 (src/screener.py)     pykrx로 전 종목 가격 수집 → 강세지속/상승전환 시그널 → 상위 30종목
2. 종목 마스터 (src/universe.py)  전 종목 티커·정식명·시총 (스크리닝 필터와 무관)
3. 수평 그래프 (src/groups.py,    KRX 테마지수 + 섹터·테마 ETF PDF로 섹터 초월 그룹 구성
              src/factors.py)     매크로 팩터(환율·구리·유가·금리) 베타 = 부호 있는 노출도
                                  2팩터 모델로 그룹별 미반영 갭 산출
4. 관계 그래프 (src/graph.py,     밸류체인 YAML의 회사명을 티커로 해석 → 수직축 엣지
              src/graph_build.py) 그룹·팩터 노출 → 수평축 엣지 → 통합
5. 근거 수집 (src/collect.py)     네이버 뉴스 API + DART 공시 목록
6. 원인 분석 (src/analyze.py)     Claude API — 원인 7유형 분류 + 회사고유/산업공통 판정
                                  + 수직/수평 축 판정 → **해당 종목의 서브그래프만** 주입
                                  갭을 근거로 미반영 판정 후 종합 아이디어 생성
7. 리포트 (src/report.py)         reports/YYYYMMDD.html (GitHub Pages) + cases/ JSON 축적
   알림 (src/notify.py)           텔레그램 요약 발송 (+ Pages 링크)
```

**회사 고유 이슈로 오른 종목은 파급 예측에 쓰지 않습니다.** 산업 공통 요인만 확장하며,
이미 같이 오른 후보는 '기반영'으로 강등합니다.

**LLM의 역할이 바뀌었습니다.** 예전에는 밸류체인 맵 전체를 덤프해 주고 후보를 *생성*하게
했습니다. 지금은 그래프가 후보를 제시하고 LLM은 *선별하고 부호를 판정합니다.* 후보 집합이
코드로 결정되므로 재현되고, 그래프 밖에서 꺼내 온 후보는 `[그래프 밖]`으로 표시되어
사후 채점에서 그래프 기반 후보와 적중률을 비교할 수 있습니다.

## 로컬 실행

```bash
pip install -r requirements.txt
python -m src.pipeline                    # 오늘 기준 전체 실행
python -m src.pipeline --skip-analyze     # 스크리닝+수평그래프+리포트만 (LLM 키 불필요)
python -m src.pipeline --skip-horizontal  # 수평 그래프 생략 (빠른 확인용)
python -m src.pipeline --date 20260724    # 특정일 기준
```

수평 그래프는 **가격 데이터만으로 계산되므로 API 키가 전혀 필요 없습니다.** LLM 키가 없어도
그룹별 미반영 갭 랭킹은 리포트에 그대로 나옵니다.

## 자동 실행 (GitHub Actions)

`.github/workflows/daily-screen.yml`이 **평일 17:10 KST**에 파이프라인을 실행하고,
결과를 커밋한 뒤 `reports/`를 GitHub Pages로 배포한다. Actions 탭에서 수동 실행(workflow_dispatch)도 가능.

### 필요한 설정

**1. Repository Secrets** (Settings → Secrets and variables → Actions):

| Secret | 필수 | 용도 |
|---|---|---|
| `KRX_ID` / `KRX_PW` | 권장 | KRX 정보데이터시스템([data.krx.co.kr](https://data.krx.co.kr)) 계정. 최근 KRX가 대량 조회에 로그인을 요구해, 미설정 시 가격 수집이 실패할 수 있음 |
| `ANTHROPIC_API_KEY` | 권장 | 원인 분석·파급 추론. 없으면 스크리닝만 수행 |
| `NAVER_CLIENT_ID` / `NAVER_CLIENT_SECRET` | 권장 | 뉴스 수집 ([developers.naver.com](https://developers.naver.com)에서 검색 API 앱 등록) |
| `DART_API_KEY` | 권장 | 공시 수집 + **수직축 자동 구축** ([opendart.fss.or.kr](https://opendart.fss.or.kr) 무료 발급) |
| `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID` | 선택 | 텔레그램 알림 (@BotFather로 봇 생성 후 토큰, 봇과 대화 시작 후 chat_id 확인) |

**2. GitHub Pages 활성화**: Settings → Pages → Source를 **GitHub Actions**로 설정.

## 검증

세 층으로 나뉘며, 각각 다른 질문에 답합니다.

| 층 | 질문 | 방법 | 실행 시점 |
|---|---|---|---|
| 1. 단위 테스트 | 로직이 의도대로 도는가 | `pytest` (합성 데이터, 네트워크 불필요) | 모든 푸시·PR 자동 |
| 2. 스모크 테스트 | 실제 데이터로 도는가 | `smoke` 워크플로우 (라이브 KRX, 커밋·배포 없음) | 수동 실행 |
| 3. 사후 채점 | 예측이 쓸모 있었는가 | `python -m src.score` (cases/ 축적분) | 데이터가 쌓인 뒤 |

```bash
python -m pytest tests/ -v        # 1층
python -m src.pipeline --smoke    # 2층 (로컬에서 라이브 확인)
python -m src.score --horizon 10  # 3층
```

**2층은 Actions 탭 → `smoke` → Run workflow**로 실행합니다. 기준일과 LLM 분석 포함 여부를
고를 수 있고, 결과물(리포트·데이터)은 아티팩트로 7일간 남습니다. 커밋도 Pages 배포도 하지
않으므로 병합 전에 안전하게 돌려볼 수 있습니다.

**3층이 이 시스템의 진짜 검증입니다.** 미반영으로 꼽은 후보가 실제로 올랐는지, 갭이 클수록
이후 수익률이 높았는지(갭 지표 자체의 유효성), 수직축과 수평축 중 어느 예측이 더 맞았는지,
'피해'로 꼽은 종목이 실제로 하락했는지(방향 적중률)를 채점합니다. `cases/`가 며칠 이상
쌓여야 의미 있는 수치가 나옵니다.

여기에 **출처별·경로별 채점**이 붙습니다. 그래프에서 나온 후보와 LLM이 그래프 밖에서
만든 후보의 적중률을 갈라 보고, "건설·EPC→후방→시멘트" 같은 경로별 성과를 누적합니다.
**밸류체인 맵이 실제로 값을 하는지는 이 비교로만 답이 나옵니다.** 그래프 기반이 LLM
창작보다 낫지 않다면 맵은 비용만 쓰고 있는 것이고, 그 사실이 숫자로 드러납니다.

2층에는 **외부 API 계약 검증**이 있습니다. pykrx의 인덱스 타입·컬럼명·함수 존재 여부를
명시적으로 확인합니다. 1층은 픽스처를 우리가 직접 만들기 때문에 외부 API가 바뀌어도
구조적으로 잡지 못하는데(실제로 인덱스 타입 결함이 그렇게 빠져나갔습니다), 그 사각지대를
여기서 덮습니다.

### 단위 테스트가 고정하고 있는 결함들

`tests/test_alignment.py`는 **예외 없이 조용히 틀린 답을 내는** 종류의 결함을 막습니다.
실제로 개발 중에 발견해 수정한 것들입니다.

- **인덱스 정합성** — pykrx는 함수마다 인덱스 타입이 다릅니다. 전 종목 스냅샷은 티커
  인덱스를, 시계열 조회는 DatetimeIndex를 줍니다. 섞이면 정렬에 실패해 시장 수익률이
  전부 NaN이 되고, 시장 요인이 0으로 취급되어 2팩터 보정이 무력화됩니다.
- **거래정지 종목** — pandas `pct_change()`는 기본으로 결측을 앞값으로 채워 정지 종목을
  0% 수익률로 둔갑시키고, `sum()`은 전부 결측인 구간을 0으로 돌려줍니다. 둘이 겹치면
  거래정지 종목이 '전혀 안 움직인 종목'으로 보여 **미반영 1순위**를 차지합니다.
- **종목명 매칭** — LLM이 내놓은 이름이 KRX 공식 표기와 다르면 갭 주입과 사후 채점에서
  조용히 빠집니다. 정규화 후 정확 일치까지만 허용하고, 미매칭은 집계해 로그로 드러냅니다.
- **티커 주입 범위** — 사후 채점은 종합 아이디어의 티커를 읽으므로, 개별 분석에만
  주입하면 채점이 항상 0건이 됩니다.
- **서브그래프 누수** — 건설 종목을 분석할 때 조선 맵이 딸려 오면 안 됩니다. 산업 파일이
  늘어도 한 종목의 렌더 크기가 변하지 않아야 확장이 성립합니다.
- **역방향 조회** — 산업 간 관계를 한 방향만 넣으면 소형 소재주에서 출발할 때 전방
  수요처를 찾지 못합니다. 수직축이 실제로 잡아내야 하는 방향이 바로 그쪽입니다.
- **우선주 병합** — 이름 정규화가 '현대차우'를 '현대차'로 흡수하면 엉뚱한 종목에
  수혜가 귀속됩니다.
- **목차를 본문으로 착각** — DART 문서 앞머리 목차에도 'II. 사업의 내용'이 있어서,
  첫 매치를 쓰면 수십 자짜리 절을 잘라 놓고 성공한 것처럼 보입니다.
- **수치 문자 참조** — `&#183;`를 남기면 LLM은 그걸 보고 인용엔 `·`로 적어,
  **정상 관계가 인용 검증에서 환각으로 오판돼 폐기**됩니다.
- **표 행 인용** — 인용 길이 하한을 산문 기준으로 잡으면 `레미콘 | 38.0%` 같은
  가장 강한 등급 A 근거가 통째로 폐기됩니다.
- **별칭으로 접힌 제품** — 두 제품이 같은 산업으로 접히면 엣지가 중복되고 매출
  비중이 둘 중 하나만 임의로 남습니다(38%가 62%를 덮을 수 있습니다).

## 설정 조정

`config.yaml`에서 스크리닝 임계값(시총·거래대금 하한, 수익률·거래량 기준), 수평 그래프
파라미터(베타 구간, 갭 판정 구간, 최소 상관), 분석 대상 수, 모델 등을 조정합니다.

### 팩터 추가

`horizontal.factors`에 이름과 키워드만 적으면 됩니다. 팩터 대용치는 전부 **국내 상장
ETF/ETN**이라 별도 데이터 소스가 필요 없고, 티커를 하드코딩하지 않고 **종목명 키워드로
런타임에 해석**하므로 상품이 새로 상장되거나 폐지돼도 깨지지 않습니다. 매칭되는 상품이
없으면 해당 팩터만 조용히 건너뜁니다.

```yaml
- name: 리튬
  keywords: [리튬]
  exclude: [인버스, 레버리지]
```

## 수직축: 밸류체인 맵 확장

`valuechain/*.yaml`이 수직축 엣지의 원천입니다. 현재 건설·EPC, 전력기기, 조선, 반도체,
방산, 이차전지 6개 파일에서 34개 산업이 나옵니다. 같은 형식(peers / upstream /
downstream / notes)으로 파일을 추가하면 자동 반영됩니다.

**산업을 늘려도 프롬프트는 커지지 않습니다.** 해당 종목의 서브그래프만 주입하기 때문입니다.
맵 전체를 덤프하던 이전 구조에서는 확장이 곧 프롬프트 폭발이었습니다.

YAML에는 회사를 이름으로 적지만, 빌드 시 Layer 0이 티커로 해석합니다. **해석되지 않은
이름은 리포트 하단 '그래프 커버리지'에 그대로 노출됩니다** — 그게 맵의 구멍입니다.
상장폐지·사명 변경·오타가 여기서 드러납니다.

동종업계(peers)는 수평축의 테마·ETF 그룹이 이미 자동으로 커버하므로, 맵을 늘릴 때는
**upstream/downstream에 집중**하는 게 효율적입니다.

## 수직축: DART 자동 구축

```bash
python -m src.dart_extract --top-n 300        # 시총 상위 300종목 (Batch API)
python -m src.dart_extract --tickers 000720,003410 --no-batch   # 소량 즉시 확인
```

사업보고서의 '사업의 내용'에서 관계를 뽑아 `source: dart` 엣지로 넣습니다. 밸류체인
엣지와 **병합되지 않고 나란히 남습니다** — 둘이 같은 관계를 주장하면 교차 검증이고,
합치면 근거가 사라지기 때문입니다. 리포트에는 `dart+valuechain`으로 표시됩니다.

### 익명화 문제가 왜 문제가 되지 않는가

사업보고서의 매출처·매입처는 대체로 익명입니다("A사", "국내 대형 건설사"). 그래서
회사 쌍은 공시에서 만들 수 없습니다. **이분 그래프가 이 문제를 통째로 우회합니다.**
필요한 건 회사 쌍이 아니라 산업 간 관계이고, 그건 양쪽에서 독립적으로 나옵니다.

```
쌍용C&E 사업보고서 : 주요 제품 = 시멘트   / 매출처 = 건설업체
현대건설 사업보고서 : 주요 원재료 = 시멘트·레미콘
                      → '시멘트 →전방→ 건설'이 두 문서에서 각각 도출됨
```

부수 효과로 **종목명→티커 해석이 아예 필요 없습니다.** 공시는 그 회사 자신의 것이라
티커를 이미 알고, 상대는 산업으로만 표현됩니다. YAML 경로보다 구조적으로 견고합니다.

### 환각을 죽이는 장치: 인용 검증

사업보고서를 LLM에 넣고 "후방 산업이 뭐냐"고 물으면, 문서에 없어도 그럴듯한 답이
나옵니다. 그럴듯하기 때문에 사람 눈으로는 안 걸러집니다.

그래서 **모든 관계에 원문 인용을 의무화하고, 코드가 그 인용이 실제로 문서에 있는지
대조합니다.** 없으면 그 관계는 버립니다. "LLM을 믿는다"가 "부분 문자열이 있는지
확인한다"로 바뀌는 것이 요점입니다. **폐기율은 그대로 환각률의 하한**이라 매 실행마다
보고되고, 30%를 넘으면 경고합니다.

근거 등급에 따라 신뢰도가 갈립니다 — A(표에서 비중까지 확인) 0.85, B(본문 서술) 0.70,
C(제품명에서 추론) 0.55. 전부 손으로 쓴 밸류체인(0.5)보다 높습니다.

### 어휘 통제

산업명을 자유롭게 두면 '시멘트', '시멘트·레미콘', '시멘트 제조업'이 서로 다른 노드가
되어 그래프가 조용히 파편화됩니다. 기존 산업 목록을 프롬프트에 주고, 받은 뒤에도
정규화와 `valuechain/_industry_aliases.yaml`로 한 번 더 접습니다.

접히지 않은 것은 **신규 산업으로 보고**하고, 기존 산업과 접두가 겹치면 **별칭 후보로
제안**합니다. 자동 병합은 하지 않습니다 — 같은 규칙이 '반도체'와 '반도체 장비'도
잘못 붙여 버리기 때문입니다. 사람이 고르는 게 맞습니다.

### 비용

대량 추출이라 **Batch API**를 기본으로 씁니다(표준 요금의 50%, 배치당 10만 건까지).
시스템 프롬프트는 전 기업 공통이라 프롬프트 캐싱으로 추가 절감됩니다. 사업보고서
전체가 아니라 '사업의 내용' 절만 넣는 것도 같은 이유입니다. 모델은 `config.yaml`의
`dart.model`로 바꿀 수 있으나, 낮추면 인용 준수와 산업 분류 일관성이 떨어질 수 있으니
**폐기율과 신규 산업 수를 함께 보세요.**

공시는 확정된 과거 문서라 `data/dart_docs/`에 캐시하고 다시 받지 않습니다.
